# 实施与验收

使用用户显式指定的 sdlc-plan。用户要求启动开发，因此规划后直接实现，无新增产品选择待确认。本文件为本次范围记录，不更改此前变化的生命周期或审批状态。

## 范围与顺序

1. 后端契约：ChatSession.project_id；PATCH 会话项目；pending-task 的 queued_tasks；Issue 的 last_activity_at、updated_at、creator；状态目录和 timeline。
2. Mika：受保护的本机发送队列，发送瞬间保留文本、附件和项目快照并清空输入；串行 HTTP 提交、服务端 FIFO 执行。切换项目不能改写已提交消息的归属。异常回执不自动重发，失败可重试，待核对和恢复的队列需明确继续。
3. 动态：全工作区事项按 last_activity 排序并分页；待处理按状态目录的 in_review / blocked 类别独立查询与分页。已读仅保存当前版本指纹，按账号 / 工作区隔离，退出清理。查看不修改事项业务状态。
4. SwiftUI：动态 / Mika / 项目；头像打开设置 Sheet；项目列表减去重复进度组件；详情突出当前状态和主要动作，其余信息折叠；Mika 项目选择和逐条发送状态。
5. 验证：Swift 单元与异步协议测试、正常/Fixture Xcode 构建、Simulator 交互与截图、实际合成服务请求记录、发布隔离检查。验证完成后记录结果和剩余边界。

## 可观察验收

- A1 三个底部入口准确；任何首页右上角头像可到设置，关闭后保留当前页面、对话和草稿。
- A2 先发 A，服务端回复尚未返回时继续输入并发送 B、C；出现三条独立消息，HTTP 按次序提交，无丢失、覆盖或双击重复。
- A3 活跃任务支持排队时可提交下一条；老服务端不支持时保留本机队列，输入仍可用，不盲目发送冲突请求。
- A4 A 选择项目 P1、B 选择 P2；各次 POST 前使用对应项目，后续选择不修改先前消息快照。权限/项目更新失败时保留内容并停止该条提交。
- A5 超时/畸形回执保留待核对消息、不自动重发；明确失败可重试；后台/冷启动保留未交付消息但不悄悄自动发送；注销后旧作用域不能继续提交。
- A6 动态包含他人发起事项；超过 50 条可分页；待处理独立于新进展第一页，不漏掉较旧事项。
- A7 查看事项清除该版本红点；原来的待审核/受阻状态继续保留；新的业务变更重新点亮；切换账号/工作区不混淆；失败刷新不伪造空列表或成功已读。
- A8 验收使用已有 revision + suppress_run 状态写接口；409 读取最新状态，不重复提交；不把一次 Agent run 完成当作事项已验收。

## 约束

- 不做服务端修改，不伪造 demo 中的模型回复或运行环境选择。
- 本轮红点是应用内动态提示；APNs、锁屏推送、跨设备已读同步不纳入当前版本。
- 以状态目录为准显示待处理。无法直接决定的受阻事项通过 Mika 继续沟通，不虚构后端不存在的审批 API。
- 不扩大本轮到 Android、不改动现有 Android 队列工作，不把 TestFlight 上传当作开发完成的证据。
