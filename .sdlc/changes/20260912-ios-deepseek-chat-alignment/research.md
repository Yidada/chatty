### 2.1 顶栏（所有对话截图一致）

- 左：**两条不等长横线**的历史图标，包在一个约 36–40pt 的**浅灰圆形底**按钮里。
- 中：**会话标题**，居中、`.headline` 级别，单行截断。截图里的标题是**问题内容的概括**
  （如「高考出题趋势」「最小可两方式平方和的正整数」「三体剧情介绍」/
  "Trends of Gaokao questions" / "The Three-Body Problem"），说明标题来自服务端生成。
- 右：**加号在对话气泡里**的图标，同样是浅灰圆形底按钮，用于新建对话。
- 无底部 Tab Bar：DeepSeek 是单栏聊天面 + 历史抽屉。

### 2.2 空态 / 欢迎态（cn2 / us2 + 2026-09-10 真机实拍）

- 中央：蓝色虎鲸 logo。
- **当前中文主文案：「想从哪里开始？」**——依据是 2026-09-10（三模式合并当天）的
  **真机实拍新闻配图**（鞭牛士/BiaNews），已下载并逐像素复核，
  存于 `evidence/research/empty-state-20260910-bianews.jpg`。
- **`ds/cn2.png` 里的「下午好，有什么可以帮到你？」是滞后的商店营销物料**，
  不是当前版本。这是本次调研里唯一一处「一手截图本身也会过时」的案例，
  已在 `spec.md §5` 与 `§14` 标注。
- 英文问候："How can I help you?" 同样来自商店物料，**当前英文文案未知**。
- 实拍图同时确认（与商店截图一致）：左上 `≡`、右上 `⊕`、输入卡片
  placeholder「发消息或按住说话」、两个 chip、右侧 `⊕` + 语音按钮，
  **无底部 Tab Bar**。→ 结构层面两套素材一致，只有逐字文案有差异。
- 实拍图里 **`智能搜索` 处于激活态**（`#EDF3FE` 底 + 品牌蓝字与图标）、
  `深度思考` 处于未激活态（白底 + 浅描边）——这是 chip 两态的**真机**证据，
  比商店截图更可靠。
- 附件面板展开后：最近图片缩略图横条（每张右上角一个选择圈）+ 三个大圆角浅灰按钮
  `Camera / Photo / Document`（中文 `拍照 / 相册 / 文件`）。

### 2.3 输入卡片（所有截图一致）

```
┌────────────────────────────────────────────┐
│  发消息或按住说话                          │   ← 占位文案，灰色
│                                            │
│  (⌘深度思考)  (🌐智能搜索)        ⊕     ◉  │   ← chip 行 + 右侧按钮位
└────────────────────────────────────────────┘
```

- 卡片：`surface` 白底、大圆角（视觉上 ≥ 24pt，近胶囊）、细描边/极浅阴影。
- **占位文案**：中文「发消息或按住说话」/ 英文 "Type a message or hold to speak"。
- **两个 chip**：
  - 未激活：白底 + 1px 浅灰描边 + 深色文字 + 灰色图标
  - 激活：淡蓝紫填充（取样 `#EDF3FE`）+ 无描边 + 品牌蓝文字与图标
  - 中文「深度思考」「智能搜索」；英文 "Think"（原子图标）"Search"（地球图标）
  - **注意**：早期版本叫「联网搜索」，v2.5 起叫「智能搜索」——照抄旧文案会过时。
- **右侧按钮位是上下文相关的**：
  - 空输入：`⊕`（附件）+ `◉`（语音波形）
  - 附件面板展开（cn2）：`⊗`（关闭）+ `◉`
  - **截图里看不到常驻的发送按钮**，推断有文本时才出现发送；生成中应为停止（未见截图）

### 2.4 用户消息

- **右对齐淡蓝紫气泡**，取样填充 `#EDF3FE`，圆角约 18pt，深色文字，无头像。
- 多行文本自然换行（cn4 的四行问题、us3 的两行问题）。
- 文件附件：**位于文本气泡上方**的独立白底圆角卡（cn5/us5），左侧蓝色文档图标，
  主行文件名（截断，如 "The Three-Body Probl..."），副行 `TXT 1.2MB`（类型 + 大小）。

### 2.5 Mika 侧（助手）回答

- **全宽纯文本、无气泡、无头像、无背景**。
- 标题用加粗行 + 可选 emoji（`📖 第一部：《三体》`）。
- 段落、无序列表（`• 与三体文明的接触：…`）正常排版。
- **LaTeX 渲染确认**（cn4/us3）：display 公式居中（`a² + b² = n`、`N = a² + b² = c² + d²`），
  行内公式斜体衬线（`(a,b)`、`a ≠ b`）。这是 KaTeX 风格输出。

### 2.6 过程块（本次对齐的核心）

**进行中（cn3/us3）**

```
正在思考 ⌄                      ← 标题行，向下的 chevron，展开态
 • 对于"…"这部分，需要先分析…    ← 圆点项目符号 + 灰色正文
 ─────────────────────────────
 🔍 已搜索到 17 个网页  [G][G][e] ← 工具行 + favicon 药丸
 • 搜索结果展示了一些相关页面…
 ─────────────────────────────
 📄 已浏览 3 个页面     [🐧][U]
 📄 查找关键词
 • 这些资料提供了…
```

- 左侧有一条**竖向时间线 rail**，把圆点与工具图标串起来。
- 步骤行结构：**工具/动作标签 + 可选的内联附件药丸（favicon）**，下面是灰色解释文字。
- 英文对照："Found 17 web pages" / "Read 3 pages" / "Found keyword"。

**完成（cn4）**

```
已思考（用时 90 秒）›           ← 标题行，向右的 chevron，已折叠
答案：最小的正整数是50。        ← 正文紧接其后
```

- 标题文案格式：`已思考（用时 N 秒）›` / "Thought for 52 seconds ›"。
- 折叠后**只占一行**，正文成为视觉主体。

**置信度说明**：`cn3/cn4` 是 App Store 营销截图，属于**官方素材**，可视为官方对该
交互的准确呈现；但「自动折叠的触发时机」「折叠动画」「reduce motion 行为」属于行为细节，
营销截图无法证明，需真机复核（§10）。

**chevron 方向已实测确认**（从截图裁切放大后目视）：

| 状态 | 文案 | chevron |
| --- | --- | --- |
| 生成中（展开） | `正在思考` / `Thinking` | **向下 `⌄`** |
| 完成（折叠） | `已思考（用时 90 秒）` / `Thought for 52 seconds` | **向右 `›`** |

> 第三方报告的表格曾把「进行中」的 chevron 写成向右，实测裁切图为**向下**。
> 两处文案均为灰色 `#7D7F85`，不是黑色。

**关于品牌蓝**：第三方调研拿到了 DeepSeek **官方站点 CSS 构建产物**
（`https://www.deepseek.com/_next/static/css/8200fbc59b0ac2c5.css`）中的设计 token，
其中 `--ds-color-brand: #4d6bfe`（浅色）、`--ds-color-brand: #6799fe`（深色）；
官方 logo SVG 的唯一填充色同样是 `#4D6BFE`。同时 `--ds-color-static-black: #0f0f0f`
——**与我们实测的助手正文 `#0F0F0F` 精确吻合**，这大幅提高了「官方 token 与 App 呈现同源」
的可信度。

**采样蓝与 token 蓝的差异已解释**：从商店截图采样得到的蓝约为 `#426EFE`
（本次独立取样落在 `#3864FC`–`#406CFC`，与第三方一致），而官方 token 是 `#4D6BFE`。
差异方向与幅度符合 **Display P3 → sRGB 的转换偏移**：营销图经过色彩空间转换后蓝色会
偏饱和、偏亮。**结论：不要把截图采样值当规范，采用 `#4D6BFE`。**

**但仍需注意**：

1. 这是 **Web 设计系统**的 token，不是 iOS App 的实测值。同一份 token 里
   `--ds-color-bg-page: #f9f8f8`，而 App 实测页面背景是纯 `#FFFFFF`，说明两套值并不完全通用。
2. `#4D6BFE` 现在是**最高可信的候选**（官方 token + logo SVG + 截图蓝同族），
   但 **App 内实际取值仍需真机取色**。
   `spec.md` 因此采用 `#4D6BFE`，并把「真机取色」保留在复核清单里。

**深色模式的可用信号（仍非 App 一手）**：同一份 Web token 的深色块给出
`brand #6799FE`、`bg-page #0A0A0A`、`text-primary #FFF`、`text-description hsla(0,0%,100%,.56)`、
`surface hsla(0,0%,100%,.06)`。这些可以作为**深色方案的起点**，但不能当成 App 的深色规格——
`spec.md §2.1` 仍要求优先拿到真机深色截图；在拿到之前，深色令牌以系统语义色为准，
若确需自定义则以上述值为**待验证的候选**并明确标注。
完整 token 清单见 `evidence/research/deepseek-design-tokens.css`。

## 5. 用户反馈与产品质量风险（用于避免照抄缺陷）

来自 2026-09-10 更新后的社区反馈（[什么值得买汇总](https://post.smzdm.com/p/a70nwd9g/)，
转引小红书 / 知乎 / 36 氪）：

- **负面集中区**：角色扮演与情感陪伴用户抱怨「回复变短、语气变冷、人设崩」，
  单帖点赞 4000+。这是**模型行为**变化，不是 UI 变化——与本次 UI 对齐无关，但提醒我们：
  对齐的是**界面与交互**，不是 DeepSeek 的回答风格。Mika 的回答风格由 Multica 决定。
- **正面集中区**：速度与识图（工具向用户）。
- **稳定性**：更新当天服务繁忙。
  → **对 Chatty 的启示**：不要照抄 DeepSeek 的「服务繁忙」体验；Chatty 已有
  `uncertain` 核对机制与失败说明（`ChatScreen.swift:29-36`、`:146-152`），这是相对优势，
  本次对齐不应削弱它。
- 「强制更新」争议：用户关掉自动更新仍被更新。
  → 与我们的发布流程无关，但说明用户对不可回退的变更敏感；`plan.md` 因此要求
  分阶段独立可提交。

## 6. 与 Chatty iOS 现状的差距（摘要）

详细映射见 `spec.md §12`。这里只列**能力层面**的结论：

| DeepSeek 有 | Chatty iOS 现状 | Multica 是否已有能力 |
| --- | --- | --- |
| 会话历史 + 切换 | **完全没有**（只有「上次会话」恢复） | **有**：`GET /api/chat/sessions` 已带 `title/pinned/unread_count/last_message` |
| 首屏欢迎态 | `ContentUnavailableView` 空态 | 客户端即可实现 |
| 停止生成 | **没有** | **有**：`POST /api/tasks/{id}/cancel`（Android 已在用） |
| 队列单条优先/移除/清空 | 只能「整体继续发送」 | **有**：`queued-tasks` 三个接口（Android 已在用） |
| 过程块自动折叠 | 独立 `DisclosureGroup`，不随消息自动折叠 | 客户端即可实现（数据源 `TaskTrace` + `task:message` 事件） |
| 按会话独立草稿 | **按 Agent 单份**（切会话会串） | 客户端存储改造 |
| LaTeX 公式 | 降级为纯文本 | 客户端渲染能力 |
| 逐字流式 | 无 | **无**：只有过程事件 + 最终消息 |
| 思考/搜索开关 | 无 | **无**：没有请求参数 |
| 语音输入 | 无 | 无转写服务 |
| 图片理解 | 无 | 本轮范围外 |

**关键结论**：差距里**超过一半是「服务端已有能力、iOS 没接」**（历史、停止、队列），
而不是服务端做不到。这决定了 `plan.md` 的性价比排序——先把已有能力接上，
再做纯客户端的视觉与过程块，最后才是需要新增能力的公式渲染。

## 8. 对本次对齐的结论性建议

1. **对齐价值最高的不是配色，是信息架构**：会话历史 + 首屏欢迎态 + 过程块自动折叠 +
   停止/队列。前三项纯客户端，第四项服务端已有接口。
2. **不要把 DeepSeek 的「模式选择」搬过来**：它自己在 2026-09-10 就删掉了。
   同理，`spec.md` 决定不做思考/搜索开关。
3. **不要照抄「按住说话」和网页检索引用**：前者无转写服务，后者无 citation 数据结构，
   照抄就是假控件。
4. **保留 Chatty 的失败处理优势**：`uncertain` 核对、失败原因说明、离线草稿是 DeepSeek
   的弱项（服务繁忙、强制更新），不能在对齐视觉的过程中被简化掉。
5. **深色模式先不要动**：在拿到一手深色截图前用系统语义色，拿到后再替换令牌
   （视图零改动，因为令牌是集中的）。

## 9. 官方 FAQ、版本记录与社区证据（第二轮调研）

本节回答一手截图答不了的问题：历史列表长什么样、怎么操作、生成中能做什么。

### 9.1 历史是「侧边栏」，不是一级页面（高置信度）

官方 FAQ 原文（从 `static.deepseek.com/faq` 前端 bundle 读出）：

> 多端同步问题：网页端可尝试刷新页面，**APP 端可下拉刷新历史对话侧边栏**，并重新进入目标对话。

→ 官方把 App 侧历史列表称为**「历史对话侧边栏」**，支持下拉刷新。结合截图顶栏左侧的
菜单图标（`ds/cn2.png`），可以确认：**历史是左上角唤出的抽屉/侧边栏**，不是 Tab。
iPad 官方截图仍使用同一个左上角菜单图标 → **iPad 也是单栏 + 抽屉**（与 `spec.md §10`
的推荐一致）。

来源：[官方 FAQ](https://static.deepseek.com/faq/index.html?lang=zh)、
[可读镜像](https://github.com/thevibeworks/deepseek-docs/blob/main/content/zh-cn/faq/category-2.md)

### 9.2 历史行的操作是**长按**，不是左滑（高置信度）

官方 FAQ 逐字原文：

> **重命名对话标题**：… APP 端：在历史对话列表中，**长按**目标对话，选择「重命名」。
> **置顶历史对话**：… APP 端：在历史对话列表中，**长按**目标对话，选择「置顶」。
> **删除历史对话**：… APP 端：在历史对话列表中，**长按**目标对话，选择「删除」。
> **请注意：已删除的对话无法恢复，请您谨慎操作。**
> **分享历史对话**：… APP 端：**长按模型的回复内容**选择「分享」，或直接点击回复内容下方的「分享」按钮。

结论：

- 移动端历史行**没有左滑操作**；「…」三点菜单**只属于网页端**。
- **分享的对象是模型回复**（长按回复或回复下方「分享」按钮），**不是会话**。
- 删除**不可恢复**，且是官方明确语义。

> 对 `spec.md` 的影响：`spec.md §4.2` 原本写「滑动操作待定」，应改为**长按菜单**
> （重命名 / 置顶 / 删除），并去掉对左滑的猜测。Chatty 的动态页已有左滑动作体系，
> 但历史列表应遵循 DeepSeek 的长按语义，保持一致。

### 9.3 历史搜索**存在**（高置信度）

App Store 版本记录里有 "Search your chat history" / 「支持搜索历史对话」这一条。
**具体落在哪个版本号存在争议**：一份调研读作 2.1.1（2026-05-21），另一份根据 Apple
版本历史 DOM 的实际顺序（每个 `<li>` 内是 **notes → 版本号 → 日期**，按直觉解析会
整体错位一格）读作 **2.1.0（2026-05-11）**。两说均未由本会话独立验证，
**`research.md` 只采信「2026 年 5 月上线搜索」这一粗粒度结论**，具体版本号标注为
低置信度、不作为规范依据。

→ DeepSeek iOS **有**历史搜索。`spec.md §4.2` 的「本地搜索」不是超越，而是对齐；
由于 Multica 的 `GET /api/chat/sessions` 无搜索参数，**本地过滤是唯一可行实现**，
需要在规范里注明这是实现限制而非设计选择。

### 9.4 生成中的行为：可中断，且输入不被锁死（中高置信度）

来自网页端变更检测与社区 bug 报告（非官方文档，标注为中）：

- 2026-08 变更：「生成状态改为消息级追踪，**支持按消息停止/继续生成**。生成中可先输入，
  **『打断并发送』与并行流默认开启**。」
- 存在明确的 **「停止生成」按钮**与 **「继续」** 动作；有用户报告「停止后继续会恢复
  已进入的死循环」的缺陷。
- **推论（中）**：输入框在生成中**不被禁用、不排队**，而是「打断并发送」语义。

> 对 `spec.md` 的影响：`spec.md §7.2` 的「生成中 + 输入非空 → 继续排队发送」是
> Chatty 的既有语义（服务端 `supportsQueue`），与 DeepSeek 的「打断并发送」不同。
> **不要为了对齐而丢掉队列能力**；规范应显式记录这一差异（见 §12 映射表补充行）。

### 9.5 商业模式与模式历史（高置信度）

- **DeepSeek iOS 无内购、完全免费**（iTunes Lookup 无 IAP 条目）——因此没有
  ChatGPT/Claude 那种付费墙、模型选择器与额度 UI。**Chatty 不应引入**这些元素。
- 模式历史：专家模式 2026-04-08 上线 → 识图模式 2026-06-18 加入 →
  **2026-09-10 三者合并为单一对话框**；V4 Pro 于 2026-09-14 12:00 下线。
  当前输入区仅剩 `深度思考` / `智能搜索` 两个消息级开关。

### 9.6 社区痛点（用于避免照抄缺陷，高置信度，均来自 App Store 评论语料）

| 痛点 | 具体 | 对 Chatty 的启示 |
| --- | --- | --- |
| 重新生成/编辑有配额 | 普通对话约 3–6 次、编辑约 6 次触顶，是跨地区最一致的投诉 | Chatty 无 regenerate 接口（`spec.md §13`），不做 |
| 只能整段删除对话，不能删单条消息 | 用户明确要求「支持长按或滑动某条消息，单独删除」 | 服务端无单条删除接口，不做；但**不要**承诺 |
| 删除不可撤销 | 用户要求「历史删除可以复原」 | 若做会话删除（U3），必须二次确认 |
| 长对话自动滚动争抢阅读位置 | 用户反馈阅读被强制拉到底部 | Chatty 现有 `followingBottom` 逻辑已是正确做法，**保留** |
| 服务繁忙 | 发布当天大量失败；统计称年内第 18 次 | Chatty 的 `uncertain` 核对与失败说明是优势，保留 |
| 多端同步偶发不一致 | 官方 FAQ 承认，给出手动下拉刷新 | Chatty 会话列表也应提供下拉刷新 |

### 9.7 竞品基线（供对照，不必对齐）

同一轮调研产出了 ChatGPT / Claude / Kimi / Gemini 的 iOS 历史与消息操作基线
（见 `evidence/research/ios-ai-chat-interaction-baseline.md`）。与本 change 相关的两点：

- **ChatGPT iOS**：历史在侧边栏 `Recents` 分组，删除走「三点 + 二次确认」，侧边栏有
  搜索框。
- **Claude iOS**：历史列表**长按**会话 → `Rename` / `Delete`，与本轮 DeepSeek 的
  长按语义一致；支持跨会话 RAG 检索。

→ 三家在「历史 = 侧边栏 + 会话级长按管理」上是一致的行业惯例，`spec.md §4` 因此
有较强的横向依据。

### 9.8 第三轮：交互行为调研，以及与一手截图的冲突记录

第三轮（`evidence/research/deepseek-ios-interaction-research.md`，948 行，
基于 450 条 App Store 评论语料 + 网页端变更 diff）有三项高价值发现：

1. **未公告的次数上限是最大差评源**。重新生成约 3–6 次、编辑约 6 次、提问约 6 次、
   回答约 4 次触顶，官方从未公告；实测文案如
   「已达到重新生成次数上限，请稍后再试。」「消息数量达到上限，请开始新对话」。
   第三方测得 v2.1.1 评论均分从 3.88★ 掉到 2.66★。
   → **对 Chatty 的启示**：不要引入次数配额；Chatty 没有 regenerate 接口，本来就不会踩。
2. **「生成中发送」是 interrupt-and-send，不是排队**。网页端 2026-08-10 的变更 diff
   显示：生成状态改为**消息级追踪**，支持按消息停止/继续，生成中可先输入，
   「打断并发送」与并行流默认开启。**iOS 是否一致未验证**。
   → `spec.md §7.2` 保留了 Chatty 自己的队列语义（服务端 `supportsQueue`），
   并显式记录这一差异。**不要为了对齐而丢掉队列能力。**
3. **iOS 平台债**（与本次对齐的边界有关）：键盘无法换行（GitHub Issue #1249）、
   不跟随系统字号（2026-06 才补）、不支持横屏、无 iCloud 同步、无完成推送。
   → 前两条是 Chatty 已经做对的地方（`axis: .vertical` 多行输入 + Dynamic Type），
   不应回退。
4. **无广告、无内购**（Apple lookup 无 IAP 字段）。

**两项与一手截图的冲突，以截图为准**：

| 第三轮报告的说法 | 一手截图实测 | 结论 |
| --- | --- | --- |
| 「深度思考 / 联网搜索已不是两个并列手动 toggle，UI 只剩输入框下方的『深度思考』开关」 | `ds/cn2.png` 与 `ds/us2.png`（App Store **当前** v2.5.x 列表页素材）**同时**显示「深度思考」与「智能搜索」两个 chip，裁切放大后确认无误 | **截图为准**：当前版本仍是两个消息级 chip。第一轮报告的这一条是错的 |
| 「『已思考 N 秒』计时器**无任何证据**」 | `ds/cn4.png` 裁切放大后清晰显示「已思考（用时 90 秒）›」 | **截图为准**：计时器文案真实存在（`spec.md §6.3` 采用） |

> 这也是本次调研方法论的印证：**对营销截图做裁切放大与像素取样**比二手转述更可靠。
> 所有二手结论进入 `spec.md` 前都用一手素材复核过一遍。
