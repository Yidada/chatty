# DeepSeek 官方 iOS App 交互行为与质量基线调研

> **目标 App**：`DeepSeek - AI 助手` / `DeepSeek - AI Assistant`，App Store id `6737597349`，开发者 `Hangzhou DeepSeek Artificial Intelligence Co., Ltd`
> **观测日期**：2026-09-12（本文所有"抓取日"均指此日）
> **观测版本**：App Store CN = `2.5.1`（2026-09-12 发布）、US = `2.5.0`（2026-09-11 发布）；构建 `com.deepseek.chat`，iOS 15.0+，60.2 MB
> **目的**：为原生 iOS Clone 提供**交互行为 / 状态机 / 边界情况**基线，不是视觉稿
>
> **⚠️ 时效性警告**：该 App 在 2026-05、2026-06、2026-09 三次发生**破坏性交互变更**（限制次数、下线专家模式上传、三模式合并）。本文描述的是 **2026-09-12 快照**。任何 Clone 若按"用户记忆中的 DeepSeek"来做，一定会做错。

## 0. TL;DR — 六条最容易做错的结论

1. **"深度思考 / 联网搜索"两个手动开关已经不是主交互了。** 2026-09-10 官方把 `快速 / 专家 / 识图` 三个模式**合并为一个统一入口**，模式切换入口被移除，改为**服务端按输入自动调度**（判断任务复杂度 → 自动开深度思考 + 智能搜索；检测到图片 → 自动走视觉）。UI 上只留下输入框下方的**「深度思考」开关**。([潮新闻/同花顺 2026-09-10](https://news.10jqka.com.cn/20260910/c679777437.shtml)、[界面新闻 2026-09-10](https://finance.sina.cn/2026-09-10/detail-inirihnu8542006.d.html?vt=4))
2. **"自动调度"是当前最大的信任缺口**：阈值不公开。用户逐字抱怨："阈值不公开，判断不透明，我完全没法信任这个自动识别。"（App Store CN 评论 id 14533533940，2026-09-10）
3. **App 有硬性次数上限与长度上限**，且是服务端强制、跨语言一致的长期痛点：单条消息 `修改/重新生成` 约 6–7 次、`提问` 约 6 次、`回答` 约 4 次；超出后弹文案、必须开新对话。有明确 bug：**新对话也报"已达上限"**。
4. **图片理解在 App 内长期只是 OCR，不是原生视觉**。官方 FAQ 对上传失败的归因明确写着"系统未从图片中检测到可提取的文字"。多条评论直接说 "Image and photo uploads only allow for OCR"。
5. **DeepSeek 在会话管理上几乎是空白**：搜索聊天记录 2026-05 才灰度（比 ChatGPT 晚约 18 个月）、**无单条消息删除、无删除撤销、无文件夹/标签、无批量导出、置顶在语料中 0 条提及**。用户甚至不指望这些功能存在。
6. **App 内目前无广告、无内购**，且这是被反复表扬的差异点；用户对"上限"的愤怒恰恰源于它与"免费无广告"预期冲突 —— 多条评论主动要求"你直接收费吧，把次数还给我"。

## 1. 会话（Session / Conversation）模型

### 1.1 新建会话与"新会话何时被创建"

- **入口位置随版本漂移，是投诉点之一**：2025-01 有用户反馈"回答下方有『开启新对话』选项"，并建议改到右上角以免截图被遮挡（App Store CN 5★, v1.0.6, 2025-01-29）。→ 推断：早期是**消息流内嵌按钮 + 右上角**双入口。
- **图片上传会强制新开会话**（2026-04 前后，v1.8.1 时期）：`"This message will be sent to the new chat." After that, a new dialogue is created, and the correspondence is broken.`（App Store CA 1★, id 13911327926, 2026-04-01）。中文区同诉："上传一张图片就说会需要直接转到新聊天！上传一张就说要新聊天！搞毛啊！！！"（CA, id 13912880830）。→ **这是"附件打断上下文"的典型失败态**，Clone 必须避免。
- **空会话/首条消息**：语料无直接证据说明"何时落库"。→ **未验证，需真机确认**（见 §13）。

### 1.2 会话标题自动生成 — ✅ 已确认存在

用户直接对比了 ChatGPT 与 DeepSeek：

> "**每个对话的标题为第一个提问开头的字，不能自动生成标题**；然后你们 Deepseek 的话，**它的每个对话都能自动生成标题**，有滑动栏，回答不满意可以刷新，而且保留之前的回答可以随时看、提问可以被修改重新回答不占页面"
> — App Store CN 4★, v1.5.4, 2025-12-15（对比对象为某 ChatGPT 客户端）

→ **DeepSeek 的会话标题是模型摘要生成，而非首句截断。** 这是相对竞品的正向差异，Clone 应保留。生成时机/是否可手动改名后的覆盖行为：**未验证**。

### 1.3 会话列表操作：重命名 / 置顶 / 删除 / 搜索

官方 FAQ 给出了**平台差异明确**的操作路径（这是"APP 端 vs 网页端"少有的官方明文差异）：

| 操作 | 网页端 | APP 端 |
|---|---|---|
| 重命名 | 历史对话列表 →「…」菜单 →「重命名」 | **长按目标对话** →「重命名」 |
| 置顶 | 「…」菜单 →「置顶」 | **长按目标对话** →「置顶」 |
| 删除 | 「…」菜单 →「删除」 | **长按目标对话** →「删除」 |
| 分享 | 「…」菜单 / 回复下方分享按钮 / 右上角分享 | 长按回复内容 →「分享」，或回复下方「分享」按钮 |

来源：官方 FAQ `https://static.deepseek.com/faq/index.html?lang=zh#/category/2`（抓取日；镜像 `https://raw.githubusercontent.com/thevibeworks/deepseek-docs/main/content/zh-cn/faq/category-2.md`）
官方补充："**已删除的对话无法恢复，请您谨慎操作。**"

**关键交互事实：APP 端会话操作全部走「长按」手势，没有 trail-swipe、没有「…」按钮。** 这与报告 §9 的文本选择问题同源 —— 长按语义被会话管理占用。

**用户痛点（已验证）**：
- **无批量删除**：「不能批量删除导致只能一个个手动长按删除，操作很麻烦，要删也只能一次全删光，但是有一些历史对话是不能删掉的就使得体验很糟糕」（CN 4★, v2.3.1, 2026-08-03）
- **无删除撤销**：「還有能不能出一個歷史刪除可以復原的，有時候不小心誤刪很煩」（TW 2★, v2.2.2, 2026-07-21）
- **无单条消息删除**（只能整段删会话）：「聊天框只能整体删除，不能单独删某一条。」+ 请求「支持长按或滑动某条消息，单独删除」「可提供一天内恢复功能」（CN 5★, v2.5.0, 2026-09-10）
- **置顶/重命名的投诉：语料 0 条** → 不是"没人要"，而是**用户已不指望**。

### 1.4 聊天记录搜索 — 存在，但很晚且曾灰度

- **上线时间**：App `2.1.1`（2026-05-21）更新日志："**支持搜索历史对话**"（Apple 官方 lookup API 更新日志）
- **交互形态**：侧边栏**顶部出现"搜索聊天内容"搜索框**，输入关键词后显示包含该词的多条历史聊天记录，**点击任意一条即可定位至具体聊天位置**。网页端为左上角放大镜。
  来源：[IT之家 2026-05-12](https://m.ithome.com/html/949303.htm)（实测 App 版本 `2.1.0 (213)`）
- **官方定性**：DeepSeek 回应称"该搜索聊天记录功能目前正处于**灰度测试阶段，并非全量推送**"。同一时期媒体报道："DeepSeek 正在灰度测试查询历史聊天记录"。
  来源：[IT之家 2026-05-12](https://m.ithome.com/html/949303.htm)、[网易/荆楚网 2026-05-14](http://www.163.com/dy/article/KSU1NF500556K1ZB.html)
- **灰度造成的体验不一致（已证实真机差异）**：有用户升级 `2.0.0 → 2.1.0` 后界面**完全没变**（无聊天记录搜索），而朋友的 iPhone 11 在同一版本已有新界面（US 5★, v2.1.0, 2026-05-13）。
- **上线前的高频诉求**（说明这是长期缺口）："I would give it 5 stars if it had a chat history search feature like perplexity."（CA, v1.7.2, 2026-02-06）；[chooseai 称"比 ChatGPT 晚 18 个月"](https://www.chooseai.net/news/3737/)
- **仍未满足**：用户要**文件夹 / 标签 / 归档**而非删除：「move finished or old chats into folders instead of deleting them…They stay searchable」「add tags to any chat like #urgent, #fun, or #research」（HK 4★, v2.4.1, 2026-08-24）

### 1.5 历史对话抽屉（Drawer）与打开方式

- **存在侧边栏**：「APP 端：**下拉刷新历史对话侧边栏**，并重新进入目标对话」（官方 FAQ category-3，明文承认这是同步的手动补救动作）
- **打开手势**：语料未直接描述 hamburger / 侧滑。但有一条 2026-07 的老评论把"**你点左上角按钮**"当作已发现的功能描述（"every search you do is saved in a list (**accessed top left button in the app**)"，US 5★, v2.2.2, 2026-07-15）。→ **推断：左上角按钮打开会话列表抽屉**，置信度中。
- 一次 2025-01 的评论显示早期 `v1.0.0` **"从最开始粗糙不支持多开会话"** 已修复（CN 5★, v1.0.0, 2025-01-11），说明抽屉/多会话是上线后补的。

## 2. 发送与生成生命周期

### 2.1 状态机（由证据拼合，标注置信度）

```
[输入框可编辑]  ← ★新证据：生成中**不锁输入**，可边生成边输入
   │ 点发送
   ▼
[用户消息立即上屏(乐观)] ──► [请求已发出]
   │
   ├─(A) 服务端繁忙/限流 ──────► [错误提示]  文案见 §2.4
   │                                   │
   │                                   └─► 用户需手动重试(无幂等保证，见 §2.4)
   │
   ├─(B) 到达长度/次数上限 ────► [弹"已达上限"文案]，**发送被拒**
   │
   ├─(D) 高频发送 ─────────────► ["频繁"拒绝]，**一段时间内完全无法发送**
   │
   └─(C) 正常 ──► [per-message 三态: generating]
                        │
                        ├── 用户点「停止生成」 ──► [stopped] ──► 可「继续」[continued]
                        │                          ⚠️ 已知缺陷：继续会恢复死循环(§2.2.2)
                        │
                        ├── 用户输入并发送 ──► **打断并发送 (interrupt-and-send)**；支持并行流
                        │
                        └── 正常流式 ──► [深度思考流式块(若触发)] ──► [正文流式]
                                              │                        │
                                              │  结束时 **自动折叠**    │
                                              │  (2.5.0 新增)           │
                                              ▼                        ▼
                                         [思考块折叠态]          [回答完成]
                                                                    │
                          底部右下角「转圈箭头」重新生成 ◄──────────┘
                          (不消耗输出次数 — 见 §2.3 卡 bug)
```

> ⚠️ **本状态机是"App 端证据 + Web 端新证据"的拼合体**，两者的三态/打断并发送行为**是否在 iOS App 2.5.1 上一致，尚未验证**。见 §13 P0-4 / P0-5 / P0-6。

### 2.2 生成中能否再发送？是否有队列？

> **⚠️ 本节结论在调研末期被新证据修正，请完整阅读 2.2.1 与 2.2.2。**

#### 2.2.1 【新证据，推翻"发送键变停止键 / 输入禁用"的常见猜测】Web 端为 per-message 三态 + 打断并发送

一份对 `chat.deepseek.com` 前端产物的**可复核变更检测**（给出了 Commit ID `a610cb2→04c4137` 与 JS 哈希，日期 2026-08-10）逐字记载：

> "生成状态改为**消息级追踪**，支持**按消息停止/继续生成**。影响：**生成中可先输入**，'**打断并发送**'与**并行流默认开启**。"
> "风险：发送/停止逻辑重构，建议回归多流并发与隐私模式场景。"

→ **含义：至少 Web 端自 2026-08-10 起**，生成状态是 **per-message**（`generating / stopped / continued` 三态），输入框**不被禁用**，用户可以**边生成边输入**，并触发 **interrupt-and-send（打断并发送）**，且**支持并行流**。

**置信度：中**（来源为 linux.do 的前端包 diff 分析，可复核但非官方；本报告未能独立抓取 linux.do 原文 — 该站搜索 API 被拦截。**未在 iOS 端验证**。）

#### 2.2.2 App 端证据：仍存在"限流拒绝"，与 2.2.1 并不矛盾

- **未找到任何"发送队列（queue）"证据**（中英文语料 + 官方文档均无）。→ 仍**无排队机制**。
- **限流拒绝是明确存在的**：
  - 「聊一总会就显示**聊天过快不允许发布**的提示，并且说要等一会。这令人困扰，**实际上根本不能再发消息**，必须删除软件等十几分钟才能好一次」（CN 4★, v2.3.1, 2026-08-02）
  - 「我正在跟这个 AI 出入新生聊得上头的时候就直接来了一句**频繁**，我去直接给我想说的话都给结束了好吧」（CN 2★, v2.4.5, 2026-09-10）
  - 英文："Often **stops conversation if messages are 'too frequent'**"（US 1★, v2.2.2, 2026-07-27）
  - "**Messages too frequent**" 作为独立错误串（US 5★, v1.7.9, 2026-03-04）
- → **结论（综合 2.2.1 + 2.2.2）**：**"生成中"本身不锁输入**（支持边生成边输入 + 打断并发送，per-message 三态）；但**高频/过快发送会被服务端以"频繁"为由拒绝，且拒绝后一段时间内完全无法发送**。这是极差的体验态，Clone 必须改为**本地排队 + 可见队列 + 明确的可解释状态**。
- **"停止生成"存在，但"继续"会恢复死循环（Web 端报告）**：
  > "手动点击'**停止生成**'按钮可以暂停思考，**点继续还是会继续**"（GitHub Issue #1587，2026-08-17）
  > 长对话 10+ 轮后无限重复，"**必须由用户手动点击'暂停'按钮才能中断**"（Issue #1550，2026-08-07）
  → **含义：停止/继续的状态机不干净 —— `continued` 会连同错误的推理循环一起恢复。** Clone 必须在 continue 时重建干净的生成上下文。
  ⚠️ 上述 Issue 编号由子代理提供，**本报告未能独立打开核对**；标为**中低置信度**。

### 2.3 重新生成 / 修改 / 继续

- **存在"修改"与"重新生成"，但都被计数限制**（见 §2.5）。
- **"重新生成"的形态与位置**：**底部右下角有一个转圈箭头标志**，点一下重新生成该轮，且用户报告**不消耗输出次数**：
  > "而且还能在**对话的最底部右下角找到一个转圈的箭头标志**，点一下就能重新让 AI 写这一次的对话，**而且还不消耗输出次数**！"
  > — App Store CN 5★, v2.3.3, 2026-08-14（标题「如何在对话中卡bug」）
  → 即存在**两条重生成路径：带配额的"修改/重新生成" 与 不带配额的转圈箭头**。这是一个明显的产品不一致（用户称之为"卡bug"）。
- **曾有"重新生成的选长选短"选项，在合并中被取消**：
  > "新更新的对话模式整成三合一了，**重新生成的选长选短也取消了**，反向更新你是懂的"（CN 1★, v2.4.5, 2026-09-10）
- **"继续生成"（continue）**：语料无直接证据。→ **未验证**。
- **"修改输入"的语义**：修改原问题后重新回答，且**不新增消息占用页面**（CN 4★, v1.5.4：「提问可以被修改重新回答不占页面」）。→ 推断为**原地替换 + 分支**；官方 FAQ 确认存在分支："检查内容是否位于对话分支中：**点击对话（提问或回答）下方的数字箭头，可切换查看不同分支**"（FAQ category-3）。

### 2.4 失败 / 超时 / 断网 / 重试语义与重复发送风险

**官方文案（API 侧，可作为 App 文案的近似）**：
- `500 服务器故障` → "请等待后重试。若问题一直存在，请联系我们解决"
- `503 服务器繁忙`（服务器负载过高）→ "请稍后重试您的请求"
- `429 请求速率达到上限` → "请合理规划您的请求速率"
来源：`https://api-docs.deepseek.com/zh-cn/quick_start/error_codes`（抓取日）

**App 内实际出现的错误串（用户逐字引用，已证实）**：
| 文案 | 出处 | 逐字可信度 |
|---|---|---|
| `服务器繁忙，请稍后再试。` | JP 评论标题即复读 3 次（2025-04-15）；SG 英文用户 "I got same error messages more than 10 times in couple of days"（2025-02-11） | **中**（用户引用，非官方文案页） |
| `Server is busy. Try again later, or use Instant mode.` | Reddit 帖标题（2026-05-19，经 `.rss` 取得） | **中**（单一帖标题；但与官方 `2.5.0` 更新日志 "Instant, Expert, and Vision modes" 用词一致） |
| `Server is busy, please try again later.` / `Check Network and Retry` | US 5★, v1.7.9, 2026-03-04 | **高** |
| `客服繁忙` | 「好是好，但为什么有时候告诉我**客服繁忙**？AI 也会烧脑吗？」（CN 4★, v2.4.5, 2026-09-10） | **高** |
| `消息数量达到上限，请开始新对话` | 「刚聊的好好的…就会出现一个『消息数量达到上限，请开始新对话』，这无疑是扫兴的🙂，**关键是不能继承**」（CN 4★, v2.4.4, 2026-09-05） | **高** |
| `已达到重新生成次数上限，请稍后再试。` | 「然后弹出来一行字。**『已达到重新生成次数上限，请稍后再试。』**」（[腾讯云社区转载，2026-06-01](https://cloud.tencent.cn/developer/article/2680033)） | **高** |
| `修改输入次数超过限制，消息未发送` | Google Play 中文区（用户 Tang Junshen, 👍36, 2026-06-02） | **高** |

> **⚠️ 中文"服务器繁忙，请稍后再试"的官方逐字性未能证实**（官方 FAQ / 用户协议 / API 文档中**没有**这句面向 App 用户的文案；API 文档的官方措辞是 `503 服务器繁忙` → "请稍后重试您的请求"）。设计 Clone 文案时请视为**用户口径**而非官方口径。
>
> **另一类失败态：流式静默挂起（Web 端报告）**——无 `finish_reason`、无 `[DONE]`、连接不关闭（Issue #1608）。Clone 必须设置**客户端流空闲超时**（如 30–60s 无 chunk 即判定失败并可重试），不能只依赖服务端关闭连接。⚠️ **中低置信度**（Issue 未独立核对）。

**重复发送风险（已证实的设计缺陷）**：
> "**重新生成和修改定为 6 条的意义是什么？**…我把我一个对话框里的内容**全选复制链接**后发给了新的对话框，但是它**解读出来的最后一条，是我前对话里的最前面部分**，也就是说根本解读不出来，那你这个**分享是干什么用的？**"
> — App Store CN 1★, v2.4.5, 2026-09-10

→ **含义**：复制/分享整段对话后再粘贴到新会话，**消息顺序被破坏**（取到最前段而非最后段）。这是**消息排序保证**的真实缺陷，Clone 必须用稳定序号/时间戳 + 服务端序列号双保险。

**超时**：官方 API FAQ 明确"如果 **10 分钟**后请求仍未开始推理，服务器将关闭连接"（`content/zh-cn/faq/category-4.md`）。App 侧超时阈值：**官方未说明**。

### 4.2 【关键新证据】引用格式：内联数字标记 + 文末 Sources 列表

一份引用 GitHub Issue #1626（2026-09-04）的记载给出了目前最具体的引用形态描述：

> "**automatically appends inline citations and reference markers (e.g., `[Reference 1]`, `[citation:2]`)… a 'Sources' list at the end**… There is **no standalone setting to keep Web Search active while disabling the automatic citation behavior**."

→ **含义**：
1. 引用是**自动附加**的，形态是**内联数字引用标记**（`[Reference 1]` / `[citation:2]` 风格），**不是** superscript chip（上标小角标）。
2. 答案**末尾有独立的 "Sources" 列表**。
3. **引用行为不可单独关闭**（不能"保持联网但不要引用"）。

**置信度：中低**（单一 Issue 描述；本报告未能独立打开核对该 Issue。**且未在 iOS 端验证**——iOS 的呈现可能是角标而非方括号标记。）

5. **会话内快速滚动导航控件**

## 12. 风险与坑（会让"天真 Clone"感觉不对的东西）

### 12.1 交互状态机层面

1. **【最高危】把"深度思考 / 联网搜索"做成两个并列手动 toggle。** 2026-09-10 之后官方已合并为**单一入口 + 服务端自动调度**。做两个 toggle = 复刻 2026-09 之前的旧版。**但**：如果目标是"用户记忆中的 DeepSeek"，旧版双 toggle 反而更"对"。**必须先和产品确认对标的是哪个时间切片。**
2. **【最高危】忽略次数/长度上限。** 上限是**服务端强制**的，客户端"假装没有"会导致行为不一致。但若 Clone 自建后端，直接复制"6 次上限 + 强行开新会话"会**继承全部差评**。建议：保留"上下文长度"物理约束，**放弃"次数配额"**，并用**自动摘要/记忆继承**替代"必须开新会话"。
3. **"新会话也报已达上限"是明确 bug**，不要在 Clone 里"忠实复刻"。
4. **长按语义超载**：会话管理（重命名/置顶/删除）+ 语音输入触发 + 文本选择全都压在长按上。Clone 必须拆分（如会话行走 swipe actions + context menu，语音走独立按钮）。
5. **生成中发送 ≠ 排队。** 新证据显示 Web 端是 **per-message 三态 + "打断并发送" + 并行流**（输入**不**禁用）；而 App 端仍有"频繁"拒绝并锁死一段时间。**这两种模式不能混做**：Clone 应实现**本地排队 + 可见队列 + 可取消**，并明确"发送会打断当前生成"的二次确认（否则用户会误以为消息丢了）。
6. **失败重试缺幂等**：用户报告"重新生成后想复制重发，结果出来一个一模一样的"（CN 2★, v2.4.5, 2026-09-07），说明**重试路径可能与缓存/幂等键冲突**。Clone 需明确 requestId + 服务端去重策略。
7. **"停止生成"后"继续"会恢复死循环（Web 端报告）**：`stopped → continued` 的状态迁移不干净。Clone 在 continue 时必须**重建干净的生成上下文**而非续接旧流。

### 12.2 数据与排序

7. **消息排序必须有稳定序号**：已证实"全选复制分享到新会话后取到最后一条是最前段"的顺序破坏缺陷。不要依赖数组顺序或 createdAt 秒级时间戳。
8. **删除不可恢复且无撤销**，而官方 FAQ 明确"已删除的对话无法恢复"。Clone 若做软删 + 30 天回收站，会**比原版更好**，但用户会问"为什么 DeepSeek 没有"。
9. **无单条消息删除**：用户只能用"整段删会话"来清理几条废话 —— 这是明确的功能缺失，不是设计选择。
10. **导出只在 web**：App 端无导出。Clone 若要跨端一致，需在 iOS 也提供导出。

### 12.3 渲染与性能

11. **流式渲染粒度是敏感点**：逐行（"line-by-line at an agonizingly slow speed"）和渐进滑入（"hurts my eyes"）**都被骂过**。2.5.0 已把逐词改成渐进滑入。建议逐词插入 + 尊重 `accessibilityReduceMotion`。
12. **长对话会崩**：官方承认"历史对话内容无法加载，建议换网页端/更强设备"；用户报"思考出完但没回答出来""一条消息回几十版""段落重复两次（10 次里 8 次）"。Clone 必须做**消息级虚拟化 + 增量渲染 + 长会话降级策略**（如折叠超长历史、按需加载）。
13. **思考块比答案长**（简单问题也触发思考且重复两段）→ 官方已加自动折叠，但**没有"关闭思考"开关**（用户明确要求）。Clone 应提供。
14. **思考块可能出现负面人格评价**（"莽撞""无礼""刻薄""尖酸""啧""嚯"）→ 这是**内容安全问题**，Clone 需在 reasoning 展示层做处理或提供隐藏。

### 12.4 iOS 平台细节

15. **键盘回车 = 发送，无法换行**（GitHub Issue #1249，已 closed 但仍被报告）。Clone 必须支持 Shift/Option+Enter 或长按换行。
16. **不跟随系统动态字体**（2026-03 投诉 → 2026-06 `2.1.4` 才补"字号调整"，但用户仍嫌小）。Clone 应从第一天支持 Dynamic Type。
17. **不支持横屏旋转**（多区投诉）。iPad 支持（`iosUniversal`）但体验差。
18. **无 iCloud 同步**，会话纯服务端账号；多端同步需"下拉刷新侧边栏"。
19. **图片上传会强制新开会话** —— 这是最反直觉的失败态，必须避免。
20. **无法只发图片不配文字**（"For creative people, this is a big problem"）。
21. **语音输入松手即发、不能校对** → 典型"不可撤销动作"，Clone 应保留草稿。

### 12.5 商业与预期冲突

22. **用户对"免费无广告"有强预期**：愤怒点不是"要收钱"，而是"**不公告就偷偷降级**"。若 Clone 要限流，必须**事前可见、可解释、可预期**（如显示剩余额度）。
23. **不要复刻 App Store 更新日志的"隐瞒"**：v2.1.1 更新日志只写 bug fix 却移除专家模式联网/上传，直接导致 3.88→2.66 的评分崩塌。这是**反面教材**，Clone 的 changelog 必须写 breaking changes。
24. **"模型变笨"是主观但高频的投诉**：Clone 若替换模型/改 prompt，需准备"人格/文风一致性"回归测试，否则会收到同型差评。

## 13. Unknowns / 需要真机验证

按优先级排序。每项都需在真机（iOS 26 + App 2.5.1）上录屏取证。

### P0（阻塞设计，必须先做）

1. **联网搜索引用的完整交互**：内联角标是上标数字还是 `[1]`？点击是 App 内 webview、SFSafariViewController 还是复制链接？是否有答案末尾"来源"列表？列表项的字段（favicon/title/domain/时间）？→ 录屏 + 截图。
2. **输入框下方到底有几个按钮、分别是什么**（用户说"下面两个按钮"）→ `深度思考` + ?（是否还残留 `联网搜索`？还是 `+` 附件入口？）位置、尺寸、激活态视觉。
3. **思考块的完整状态机**：开始思考时是否自动展开？流式时是否可手动折叠（手动折叠后是否被强制重新展开）？结束时的折叠动画时长？折叠态文案（是"深度思考"还是"已深度思考 N 秒"）？**是否存在计时器**？
4. **发送中的 UI**：发送按钮是否变成停止按钮？停止后的消息状态（保留半截文本？标记"已停止"？能否 continue？）→ 直接决定 §2.1 状态机的准确性。
5. **生成中能否编辑输入框 / 发送第二条**：是 disable、排队、"频繁"提示，还是 **interrupt-and-send**？（Web 端证据指向后者；iOS 未验证）
6. **【新增】iOS 是否复刻了 Web 的 per-message 三态**：能否对**某一条**消息单独执行停止/继续？"并行流"是否在 iOS 上也默认开启？多流并发时 UI 如何呈现？
7. **【新增】自动滚动策略**：流式时是否强制吸底？用户上滑后是否解除跟随？是否有"回到底部"按钮？缓动曲线（用户报"先加速后减速"致晕眩）？是否尊重 `accessibilityReduceMotion`？

### P1（影响核心体验）

9. **附件面板形态**：`+` 打开的是什么？相册 / 拍照 / 文件 三个入口？各自动作？是否如传闻"强制新开会话"（2026-09 是否已修）？**上传后 Instant/Expert 滑块是否变灰不可交互**（子代理报 Issue #1231，待核）？

11. **附件预览与移除**：缩略图样式、是否有 X、多附件是否横滑、上传进度态、失败态。
12. **语音输入交互**：长按 or 点击？是否有波形/时长？松手即发还是可编辑？是否有"转文字后保留草稿"选项？识别中/失败态。
13. **侧边栏抽屉**：打开手势（左上角按钮？边缘侧滑？）、宽度、遮罩、会话行元素（标题/时间/置顶标记）、长按菜单项与顺序、搜索框位置与空态/结果高亮/跳转定位。
14. **新会话入口**：右上角 `+`？侧边栏顶部？首条消息何时落库、何时生成标题（发送后 N 秒？首 token 后？）、标题是否覆盖用户重命名。
15. **次数/长度上限的当前真实状态**（2026-09-12）：还剩下哪些配额？弹窗文案与出现时机（发送前预判 vs 发送后拒绝）？新对话是否仍报上限？

### P2（长尾与一致性）

18. **长会话性能基线**：100 / 300 / 500 条消息下的滚动帧率、内存占用、首次加载耗时；是否有虚拟化；官方"无法加载"的触发阈值。

25. **会话标题**：自动生成的具体形态（长度、是否带 emoji、重名如何处理）。
26. **多标签/多端并发覆盖**：iOS 与 Web 同时打开同一会话发消息，是否互相覆盖历史（Web 端已报 Issue #1624）；删除会话后是否出现"幽灵标题"复活（Issue #844）。
